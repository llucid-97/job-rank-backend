# Search state and match history

`user_preferences.search_state` holds the owner's current unsent search, complete search history, frozen last batch and posted-age filter. The existing preference endpoint accepts it as `searchState` and returns the database field as `search_state`. Its JSON is a whole-state replacement: callers must retain fields they do not intend to change. The server bounds the full object, individual notes, queries, source settings and batch sizes. It rejects coordinate fields; browser geolocation must only supply the chosen country, never coordinates.

`user_match_observations` belongs to an account and is independent of its `user_jobs` links, so removing an outdated job does not erase the historical score distribution. One row represents the latest score for an owner, candidate fingerprint, pipeline fingerprint, concrete provider model, source and job ID. Each batch is rejected in full unless every source and job ID belongs to the owner’s current workspace. This check does not bound all storage growth or attest model output. The API cannot prove a score is honest; the signed-in user's client records only complete, current assessments after saving them. The service-role table is not directly exposed to anonymous or authenticated clients. Each observation retains its original analysis timestamp. Reads choose the newest analysis model within a candidate/pipeline cohort and page without truncating; late replays cannot overwrite newer timestamps. Client clock skew can affect cross-device ordering; clearing the account's history calls the dedicated DELETE endpoint. Clear all is still a sequence of account-scoped operations, not an atomic transaction.

The client combines the backend policy fingerprint with its scoring and schema versions. The backend fingerprint includes fixed hosted model IDs, output limit and extraction instructions. Bump the explicit provider-policy revision in `constraint-prompts.ts` for other hosted ranking-policy changes that affect comparability. A provider silently changing the target of an alias cannot be noticed until another provider response reveals its concrete model; older or unresolved results stay unclassified when provenance is missing. The distribution is not a hiring probability.

Hosted search and job requirement extraction use separate structured workflows. Search notes are capped at 2,000 grapheme clusters and 16 KiB each; job posting text has a separate 200,000 UTF-16-unit and 512 KiB ceiling. The server constructs instructions, labels source text as untrusted data and asks for JSON; the client validates the response and checks quoted evidence. These measures do not guarantee prompt-injection resistance. Older clients can use the legacy `constraints` workflow only for prompts up to 8,192 UTF-16 units; they must refresh before extracting longer postings after rollout. The existing generic `candidateProfile` workflow still accepts up to 200,000 prompt characters for older clients, and a signed-in caller could use another workflow for arbitrary content. Per-account quotas and output caps do not form an app-wide spend limit. Restricting unused generic workflows, per-account and global token budgets, and a moderation model remain future work.

Apply the additive migration before deploying clients that use these fields and routes. These changes have not been applied to a live database by this branch.
