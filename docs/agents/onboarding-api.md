# Onboarding API

`GET /v1/onboarding` returns `{data: {draft, revision}}`; a missing draft is `{draft: null, revision: 0}`. `PUT /v1/onboarding` accepts `{draft, expectedRevision}` and returns the saved draft/revision. Revision mismatch returns `409 ONBOARDING_CONFLICT`. Draft source document IDs must identify active documents owned by the authenticated account.

`POST /v1/onboarding/assist` accepts `{draft, mode}` where mode is `background`, `lanes`, `interview`, or `review`. Suggestions are validated against a strict schema and tailoring evidence must quote current user-provided text.

`POST /v1/onboarding/lane-profiles` accepts `{expectedRevision}`. It prepares all lane skill and explicit-interest profiles in one setup request, persists them in the account-owned draft JSON, and returns the usual `{data: {draft, revision}}` snapshot. A cache hit returns the current snapshot without another provider call. Profile fields are invalidated when reviewed background, lanes, brief, interview answers, or source document IDs change. Active CV identity and evidence contents are part of `matchingSourceKey`.

`POST /v1/onboarding/match-jobs` accepts `{jobIds, expectedRevision, matchingSourceKey}` for up to 12 jobs saved by the account. It calls the backend Jev client, not OpenRouter, and returns `{data: {revision, matchingSourceKey, results, failedJobIds}}`. Successful jobs have one result per lane: `{jobId, laneId, score, skills, interests}`. Lanes are alternatives; callers use the highest available lane score. Skills with relevance `<= 0.25` are excluded from the skill-score denominator. Scores are ordinal match summaries, not probabilities. An interest whose TypeSafe level-1 probability is dominant (including ties), or whose probability distribution is absent/invalid, is marked unknown with `match: null`. Per-job Jev failures appear in `failedJobIds`; other jobs can still return results. The backend does not persist job annotations, so clients may cache them against the job content and `matchingSourceKey`.

For a local preview, copy `.env.example` to the ignored `.env` file and fill in valid local Supabase and provider credentials. Then use `HOST=127.0.0.1 PORT=5193 npm run dev` for TypeScript watch mode, or run `npm ci`, `npm run build`, then `HOST=127.0.0.1 PORT=5193 npm start` for the built server. Both commands bind only to loopback when these variables are set.

The known skills and interests components use a 70/30 blend; if only one is known, that component supplies the score. If neither is known, the score is null. This is a ranking heuristic, not a calibrated probability. Jev scores are fractional expected values, as described in the [official Score response contract](https://docs.typesafe.ai/primitives/score); do not require integer answers.

Local validation on 18 October 2026 passed TypeScript type checking, six focused mocked tests, all 40 existing tests, and the production build. Focused tests verified concurrent setup deduplication, cache reuse, relevant-input invalidation, stale revision rejection, fractional scoring, relevance cutoff, and explicit unknown interests. Tests used synthetic credentials and mocked provider responses; no live paid-provider accuracy or account end-to-end claim follows from them. No database migration is required.
